## 1. P1 工程地基

### 1.1 做之前的状态（问题是什么）

- LLM 调用分散：行程生成在 Node 里直接调，RAG 在 Python 里用同步 `requests` 调，各自写错误处理，没有重试和熔断。
- 错误格式五花八门：`{error:'proxy_failed'}`、`{detail:...}`、厂商原始报错直接透传给前端。
- 配置散在 `.env` 平铺变量里，Python 和 Node 各读各的，写错了要到运行时才发现。
- 只有 `console.log`，出了问题无法把一次用户请求在两个服务里的日志对上。

### 1.2 做了什么

| 模块 | 做法 | 关键代码 |
|---|---|---|
| 服务拆分 | `rag_service` → `agent_service`，拆为 `core/`（基础设施）、`rag/`、`classifier/`；Node 只做网关 | `agent_service/` |
| 配置 | pydantic-settings：`config.yaml`（非敏感）+ `.env`（密钥）+ 环境变量（`LLM__MODEL=x` 双下划线覆盖嵌套字段）；相对路径统一按项目根目录解析 | `config.py` |
| 错误码 | 枚举 + 规格表（HTTP 状态、是否可重试、提示语）；`AppError` 由全局异常处理器统一输出 | `core/errors.py` |
| LLM 客户端 | httpx 异步；`asyncio.Semaphore` 限并发；按状态码与响应体把厂商错误翻译成错误码；重试 + 熔断；每次调用记录用途、耗时、token | `core/llm.py` |
| 熔断器 | 三态：关闭 → 连续失败达阈值打开 → 冷却后半开放行一次试探，成功关闭、失败重新打开 | `core/resilience.py` |
| 日志 | JSON 行，`contextvars` 保存 request-id；按天滚动保留 14 天，错误单独一个文件 | `core/logging.py` |
| 网关 | request-id 生成/透传、统一错误、下游超时、`/api/readyz` 聚合、只托管页面 | `server.js` |

### 1.3 关键设计决策（面试常问“为什么”）

1. **哪些错误重试？** 只重试“过一会儿可能好”的：超时、429、5xx。额度不足（DeepSeek 402 / DashScope 403 + `AllocationQuota`）、鉴权失败、参数错误重试也没用，反而浪费时间。
2. **哪些错误计入熔断？** 只有“服务端不可用”类（超时、5xx、429）。额度不足不代表服务挂了，计入熔断会把“欠费”误判成“故障”。有单元测试覆盖这一点。
3. **为什么自己写熔断/重试而不用 tenacity、pybreaker？** 逻辑只有几十行，自己写能精确控制“哪些错误码重试/熔断”，并且面试能讲清每一行；依赖少。
4. **为什么 Agent 编排放 Python、Node 只做网关？** 检索、模型推理、后续图数据库驱动都在 Python 生态；网关负责边缘职责（静态托管、密钥隔离、请求追踪）。
5. **为什么不直接上 LangChain？** 项目规模小，自研代码可控、易调试；简历上能说清楚原理比“调了一个框架”更有说服力。
6. **request-id 为什么放在 body 解析之前？** 否则请求体 JSON 非法时，解析失败的错误响应里没有 request-id（实际踩到过，见 1.5）。

### 1.4 怎么验证的

- 单元测试：熔断三态与半开失败、只重试可重试错误、各厂商错误码映射、用 `httpx.MockTransport` 模拟“503 后成功”“402 不重试”“连续 500 触发熔断”。
- 降级实测：另起一个实例，把 LLM 地址指向不存在的端口：
  - `/search` 仍返回检索片段，`degraded: [query_rewrite, llm_rerank, answer]`
  - `/classify` 返回默认标签，`source: "default"`
  - `/itinerary` 返回 `UPSTREAM_LLM_UNAVAILABLE` 统一错误
  - 3 次失败后 `/readyz` 显示熔断器 `open`
- 链路追踪：带固定 `X-Request-ID` 请求，在 `logs/agent.log` 中查到同一 ID 的 LLM 调用记录与访问记录。

### 1.5 遇到的问题（讲故事用）

1. **静态资源暴露整个项目**：`express.static(__dirname)` 把项目根目录当静态目录，`config.yaml`、`data/`、日志、Python 源码、向量库文件都能直接下载（`.env` 因为 dotfiles 默认忽略才幸免）。改为只开放三个页面和 `src/`，逐个验证返回 404。
2. **测试把机器内存跑到 9.7GB**：测试里用 `monkeypatch` 替换 `core.resilience.asyncio.sleep`，但那其实就是全局 `asyncio.sleep`，替换后的函数又调用 `asyncio.sleep`，变成调用自己。修复：在模块内保存引用 `_sleep = asyncio.sleep`、`_now = time.monotonic`，测试只替换模块属性。**教训：monkeypatch 要打在“被使用的位置”，而且不要打在共享的全局对象上。**之后加了内存上限守护脚本再跑测试。
3. **请求体非法时缺 request-id**：中间件顺序问题，把 request-id 中间件挪到 `express.json()` 之前。
4. **localhost 与 127.0.0.1**：曾让 Node 只监听 `127.0.0.1`，结果浏览器用 `localhost` 访问时走 IPv6 `::1` 连不上，改回默认监听；真正的风险点（入库接口）已从网关移除。

### 1.6 可能被问到的问题

- **Q：重试会不会把下游打挂？** A：指数退避加随机抖动（0.5~1.5 倍），最多 3 次；熔断打开后直接快速失败，不再请求；并发闸门限制同时在途的 LLM 调用。
- **Q：熔断器半开状态怎么处理并发？** A：半开时只放行一个试探请求（`_half_open_in_flight` 标记），其他请求仍快速失败；试探成功关闭，失败重新计时。
- **Q：为什么用 contextvars 存 request-id？** A：asyncio 下每个请求是一个任务，contextvars 在任务间隔离，线程局部变量在异步代码里不可靠。
- **Q：配置写错了会怎样？** A：pydantic 在启动时校验类型和范围（如端口 1–65535），失败直接退出并指出字段；网关启动时也校验端口和下游地址。

## 2. P2 RAG 2.0

### 2.1 做之前的状态

纯向量召回（bge-small-zh + Chroma）+ LLM 重排；没有任何评测，无法回答“检索效果好不好、改了之后好了多少”。

### 2.2 数据问题（先修数据，再谈算法）

1. **语料是两个 CSV 拼起来的**：第 137 行是混入的表头；后半部分 `id` 又从 `row_0` 开始，217 篇中有 82 个 ID 重复。第一次抽元数据时按 `id` 存，结果一篇云南笔记被覆盖成了贵州，217 篇只剩 135 条。
   - 修复：笔记 ID 改为 `md5(标题+正文)` 前 12 位（稳定、唯一、重复导入幂等），原 `id` 保留为 `csv_id`；读取时跳过与列名相同的行，按内容去重。
2. **元数据**：用 LLM 为每篇笔记抽取城市、省份、景点、适用人群、季节、预算，增量写入 `data/notes_metadata.jsonl`（已抽过的跳过），共 217 次调用。

### 2.3 检索流程

```text
查询 → 地名识别（语料地名词典，最长匹配，不调 LLM）
     → 限定到涉及该地的笔记（结果不足 top_k 时自动放宽）
     → 向量召回 30 条 ┐
     → BM25 召回 30 条 ┴→ RRF 融合 → bge-reranker 重排前 20 条 → top_k
```

| 组件 | 实现 | 为什么 |
|---|---|---|
| BM25 | jieba 分词 + 停用词（含“宝子”“攻略”等小红书口水词）+ rank_bm25；城市、景点名加入用户词典 | 向量模型对专有名词（店名、景点名）不敏感，关键词能补上 |
| RRF | `score = Σ 1/(60 + rank)` | 只用名次，不用把余弦相似度和 BM25 分数统一尺度 |
| 地名过滤 | 用元数据构建地名词典，查询里出现就限定范围 | 语料多城市，向量检索容易把“成都美食”召回成“重庆美食”；词典匹配几乎零延迟 |
| 交叉编码器 | bge-reranker-base，只重排前 20 条，max_length 256 | 双塔向量只比较各自的向量，交叉编码器同时看查询和片段，更准但更慢 |

### 2.4 评测集怎么建（面试必问）

1. **查询**：DeepSeek 为 100 篇抽样笔记写“这篇笔记能回答的用户问题”（要求不抄标题、约七成带目的地），再按 5 个主题（美食、拍照、人群、预算季节、路线避坑）写 50 条开放式问题，去重后 186 条。
2. **候选池（pooling）**：每条查询取 4 种检索方式（向量、BM25、混合 + 地名过滤、再加重排）各自前 10 篇，加上来源笔记，取并集，平均 17.7 篇。这是 TREC 的标准做法，避免只用一种方法定义“相关”。
3. **判分**：DeepSeek 对池内每篇笔记打 0/1/2 分（2 = 能直接回答且目的地对；1 = 目的地或主题有一项对得上；0 = 不相关），共 3300 个判断。
4. **指标在笔记级计算**：同一篇笔记的多个片段只算一次。Recall@5、MRR@10 只看 2 分笔记；nDCG@5 用分级增益；没有 2 分笔记的 34 条查询不参与 Recall/MRR。
5. **人工核验**：盲标（表中不显示 LLM 分数），按 LLM 分数分层抽 60 对，用二次加权 kappa 衡量一致性。

### 2.5 结果（LLM 判分，待人工核验）

| 配置 | Recall@5 | MRR@10 | nDCG@5 | P95 延迟 |
|---|---|---|---|---|
| 向量 | 0.845 | 0.846 | 0.775 | 17 ms |
| BM25 | 0.765 | 0.760 | 0.658 | 4 ms |
| 混合（RRF） | 0.848 | 0.869 | 0.793 | 18 ms |
| 向量 + 地名过滤 | 0.845 | 0.848 | 0.801 | 29 ms |
| 混合 + 地名过滤 | 0.854 | 0.879 | 0.826 | 36 ms |
| 混合 + 地名过滤 + 重排 | 0.896 | 0.922 | 0.859 | 3.7 s |
| 再加 LLM 改写 | 0.895 | 0.930 | 0.847 | 3.2 s（不含改写） |

**能讲的结论：**
- BM25 单独不行，但与向量互补：融合后 MRR +0.023。
- 地名过滤对开放式问题帮助最大（开放式 nDCG@5 0.655 → 0.726），几乎不增加延迟。
- 重排收益最大，但延迟从 36ms 到 3.7s → **按场景取舍**：问答页开重排，行程规划不开。
- LLM 改写没有带来稳定收益，开放式问题反而下降（0.744 → 0.704）；这个配置 6% 的结果落在候选池外按不相关计，分数偏保守，暂不下结论。

### 2.5.1 指标深挖预案（这组数字最容易被追问）

**一句话版本（先背熟）：**
> 186 条查询、4 路检索结果做候选池、0/1/2 分级标注；基线是纯 bge 语义召回，最终方案是“地名过滤 + BM25/向量 RRF 融合 + bge-reranker 重排”，nDCG@5 0.775 → 0.859（+10.8%），Recall@5 0.845 → 0.896（+6.0%），MRR@10 0.846 → 0.922（+9.0%）。

**Q1：评测集怎么来的？多少条 query？relevance 怎么标？**
- **186 条查询**：
  - 136 条“基于笔记”：随机抽 100 篇笔记（固定随机种子），让 DeepSeek 为每篇写“这篇笔记能回答的用户问题”。要求口语化、不抄标题、约七成带目的地；部分笔记生成了不止一条。
  - 50 条“开放式”：给出语料覆盖的 40 个目的地，按 5 个主题（美食 / 拍照 / 特定人群 / 预算与季节 / 路线与避坑）各写 10 条，一半带目的地。
- **候选池（pooling，TREC 做法）**：每条查询取 4 种检索方式（纯向量、纯 BM25、混合 + 地名过滤、再加重排）各自前 10 篇笔记，再加上生成该查询的来源笔记，取并集，平均 17.7 篇/查询。
- **分级标注**：DeepSeek 对池内每篇打 0/1/2，共 3300 个判断（0 分 1897、1 分 1045、2 分 358）。
  - 2 = 能直接回答问题且目的地对
  - 1 = 目的地或主题只对上一项
  - 0 = 不相关
- **人工核验**：盲标（表里不显示 LLM 分数），按 LLM 分数分层抽 60 对（每档 20），用二次加权 kappa 衡量一致性。第一轮因人工标注仓促（kappa 0.25）作废并存档，换新样本重标。
- **统计口径**：
  - 笔记级计算，同一笔记的多个 chunk 只算一次。
  - Recall@5 / MRR@10 只认 2 分笔记；152 条查询有 2 分笔记，参与这两个指标；另 34 条没有，只参与 nDCG。
  - nDCG@5 用分级增益 2^g − 1。
  - 池外笔记按不相关计。

**Q2：baseline 0.775 是纯 bge 语义召回吗？**
- 是。`BAAI/bge-small-zh-v1.5` 向量（归一化）+ ChromaDB（HNSW、余弦距离），**不做地名过滤、不重排、不做查询改写**。
- 召回 40 个 chunk 后按笔记去重取前 10。
- 语料是 217 篇笔记，按 400 字、80 字重叠切成 382 个 chunk。

**Q3：混合检索里向量和全文怎么融合？加权吗？**
- **RRF（Reciprocal Rank Fusion），不是线性加权**：`score(d) = Σ 1/(k + rank_i(d))`，k = 60。
- 两路各召回前 30 个 chunk（`candidate_k`），融合后取前 30。
- 为什么不用线性加权：余弦相似度在 [0,1]，BM25 分数没有上界且随查询长度变化，线性加权要先归一化、再调权重，而 RRF 只用名次、无需调参。
- 如果追问：线性加权在有标注数据时可以网格搜索权重，可能略优，但在 186 条查询上调参有过拟合风险，可以作为后续实验。

**Q4：全文检索用什么引擎？**
- **没有用 Elasticsearch**：是进程内的 BM25（`rank_bm25` 的 BM25Okapi，默认 k1 = 1.5、b = 0.75）。
- 分词：jieba，加载从元数据得到的城市名和景点名作为用户词典（避免“宽窄巷子”被切开），并过滤停用词，其中包括“宝子”“攻略”这类小红书口水词。
- 服务启动时从向量库读出全部 382 个 chunk 构建索引，入库后重建。
- 为什么不上 ES：语料只有几百个 chunk，内存 BM25 单次查询 ~4ms，引入 ES 增加部署和运维成本却没有收益。数据量到十万级或需要实时增量、分布式时，会换成 Elasticsearch / OpenSearch（IK 分词）并保持 RRF 融合不变。

**Q5：+10.8% 是哪一部分带来的？（拆分贡献）**
- **对比口径**：基线 vs 完整方案。
- **逐步消融**（nDCG@5，相对纯向量）：

| 逐步叠加 | nDCG@5 | 相对基线 |
|---|---|---|
| 纯向量（基线） | 0.775 | — |
| + BM25（RRF 融合） | 0.793 | +2.3% |
| + 地名过滤 | 0.826 | +6.6% |
| + bge-reranker 重排 | 0.859 | +10.8% |

- **另两个指标**（基线 → 完整方案）：Recall@5 0.845 → 0.896（+6.0%），MRR@10 0.846 → 0.922（+9.0%）。
- **要主动说明代价**：重排把 P95 延迟从 36ms 拉到 3.7s，所以行程规划走不重排的路径（nDCG@5 0.826，+6.6%）。

**Q6：LLM 生成 + LLM 判分，可信吗？**
- 承认有偏差，说明做了哪些控制：
  - 候选池来自 4 种不同方法。
  - 人工盲标抽检并计算 kappa。
  - “基于笔记”和“开放式”两类查询分开报告：开放式 nDCG@5 基线 0.671 → 0.744，提升趋势与总体一致。
- 再说明局限：语料只有 217 篇，样本量有限，没做显著性检验（计划补 bootstrap 置信区间）。

**Q7：Recall@5 都 0.84 了，为什么基线这么高？**
- 语料小（217 篇），每条查询的高度相关笔记平均只有 2 篇左右，前 5 名容易覆盖。
- 而且约 3/4 的查询由某篇笔记生成，和来源笔记词面接近。
- 所以更有区分度的是 nDCG@5 和 MRR@10（排序质量），以及开放式查询的结果。

### 2.6 遇到的问题

1. **交叉编码器在 CPU 上很慢**：实测约 140ms/条候选，重排 30 条要 5 秒。测了 max_length 512/256 与候选数 30/20/10 的组合，选“重排前 20 条、截断 256”约 2.8 秒；进一步的量化/ONNX 放到 P8。
2. **LLM 判分与人工不一致**：第一轮人工抽检加权 kappa 只有 0.25。排查：先排除表格错位（把人工分数上下平移重算，一致性更差），再逐条看分歧——LLM 判 0、人工判 2 的 8 条里，多数是人工看快了（例如“北京预算”的问题配了一篇贵州笔记）。结论：第一轮作废并存档（`rag_review_round1_discarded.csv`），换一批新样本（避免记住答案）重新盲标，正文从 150 字放宽到 300 字。**教训：人工标注本身也要质控；评分标准要写成可操作的规则（“只有目的地对上最多 1 分”）。**
3. **评测脚本里的偏差**：73% 的查询由某篇笔记生成，词面重合可能偏向 BM25；报告中把“基于笔记”和“开放式”两类查询的 nDCG 分开列出。

### 2.7 可能被问到的问题

- **Q：为什么用 RRF 而不是加权求和？** A：两路分数尺度不同（余弦相似度 vs BM25 无上界），加权求和要归一化和调权重；RRF 只看名次，无需调参，k=60 是常用值。
- **Q：评测集是 LLM 生成、LLM 判分，会不会自己评自己？** A：会有偏差，所以做了三件事：候选池来自 4 种方法而不是单一方法；人工盲标抽检并计算 kappa；分开报告“基于笔记”和“开放式”两类查询的结果。
- **Q：池外文档怎么处理？** A：按不相关计（TREC 惯例），报告里列了每种配置前 5 名的“判分覆盖率”，带 LLM 改写的配置只有 94%，所以它的分数偏保守。
- **Q：为什么地名识别不用 LLM？** A：词典最长匹配零延迟、结果确定；LLM 改写实测没有稳定收益且多 1–2 秒。
- **Q：chunk 级和笔记级指标有什么区别？** A：同一篇笔记切成多个 chunk，chunk 级会把同一篇重复计分；用户关心的是“找到了哪几篇笔记”，所以按笔记去重后算。
- **Q：重排太慢怎么办？** A：只重排前 20 条；场景分流（行程规划不重排）；后续计划 ONNX 导出 + 动态量化。

## 3. P3 Agent + Function Calling

### 3.1 做之前的状态

- LLM 只输出一段“第N天 / - [城市] 景点（备注）”格式的文字，地图页用正则解析，再逐个景点做“同城 POI → 全国 POI → 地址编码”三级匹配。
- LLM 看不到任何真实数据：景点之间多远、是否存在、在不在这个城市，全靠模型记忆；路线是否顺、一天排不排得下，没人检查。
- 简历里写的 Function Calling、“工具结果回填上下文”、“校验纠错”在代码里都不存在。

### 3.2 做了什么

```text
用户需求 → 地理编码目的地（拿到 adcode）
  → LLM(tools) 循环（最多 12 轮）：
       search_notes / poi_search / route_plan / get_weather（同一轮多个调用并发执行，结果作为 tool 消息回填）
  → submit_itinerary(结构化行程 JSON) → 规则校验器
       ├ 通过：用高德实算的交通时长覆盖模型填写的值 → 返回
       └ 不通过：问题列表作为 submit_itinerary 的工具结果回填 → LLM 修正（最多 2 次）
```

| 模块 | 要点 | 代码 |
|---|---|---|
| 工具定义 | OpenAI tools 格式；`submit_itinerary` 的参数就是行程 JSON Schema，把“最终输出”也变成一次工具调用 | `agent/tools.py` |
| 工具执行 | 失败不抛异常，返回 `{ok:false, error, hint}` 让模型换关键词重试；每次调用记入 trace | `agent/tools.py` |
| 会话登记 | 本次 `poi_search` 返回过的 POI 都记在 `PlanContext.pois`，校验器只认这里面的 `poi_id` | `agent/tools.py` |
| 校验器 | 纯规则 + 高德实算，不用 LLM：结构、天数、POI 真实性、城市一致（adcode 前缀，直辖市/省取 2 位）、去重、相邻两站 ≤60 分钟、每日 ≤12 小时 | `agent/validator.py` |
| 高德客户端 | 异步；客户端限速 3 QPS；QPS 超限错误重试、其他业务错误不重试；LRU + TTL 缓存 | `core/amap.py` |
| 流式进度 | `/plan/stream` 用 SSE 推送 status / tool_call / validation；网关逐块透传，浏览器断开就取消规划 | `app.py`、`server.js` |
| 多轮修改 | 把上一版结构化行程作为 `previous_itinerary` 传回，其中的地点视为已查询过 | `agent/orchestrator.py` |
| 前端 | 一个原地刷新的进度气泡；地图页直接用已校验坐标，不再做地理编码；Agent 失败自动回退旧流程 | `ai-chat.html`、`output-map.html` |

### 3.3 关键设计决策

1. **为什么让“提交行程”也是一个工具，而不是让模型最后输出 JSON？** 校验结果可以作为这个工具的返回值自然回填，自纠就在同一个 Function Calling 循环里完成，不需要额外的“修正提示词”流程；参数还有 JSON Schema 约束。
2. **为什么校验器不用 LLM？** 规则检查结果确定、可解释、毫秒级、不花 token；“LLM 评 LLM”既慢又可能互相迁就。
3. **怎么防止模型编造坐标？** 坐标根本不让模型填——模型只给 `poi_id`，服务端按本次检索登记表回填坐标；`poi_id` 不在登记表里就判不通过。这是“幻觉防护”的核心。
4. **交通时长为什么要覆盖？** 模型估的时长不可信；校验器用高德实算每一段，既用于判断，也用于展示（标 `verified: true`）。
5. **为什么不用 LangChain / LangGraph？** 循环本身不到 200 行；自己写能精确控制：并发执行、提交与修正计数、预算保护、事件推送、trace 统计。面试能逐行讲清。
6. **SSE 而不是 WebSocket？** 单向推送进度就够了，SSE 基于普通 HTTP、网关透传简单；断开时取消后台任务，避免白花 LLM 调用。

### 3.4 怎么验证的

- **单元测试**（假 LLM + 假高德，离线确定性）：合法行程通过且坐标/路段被回填；编造的 `poi_id` 被拒；外地 POI、超长路段、天数不符、重复地点、结构错误都能识别；完整循环“查 POI → 提交错误行程 → 收到问题 → 修正 → 通过”，并检查每个 tool_call 都有对应的 tool 消息；预算保护在第 3 轮强制 `tool_choice`。
- **浏览器实测**：西安 2 天 49 秒（13/13 地点、11/11 路段实算）；追加“第二天下午太累，去掉大雁塔换个喝茶的地方” 15 秒完成局部修改；地图页 0 次地理编码。
- **对比评测**：见 3.5。

### 3.5 评测与结果（`eval/agent_report.md`）

**怎么测的（先背熟）：**
- 20 个出行需求、20 个城市（其中 4 个城市不在笔记语料里），1~3 天，不同偏好与补充要求（带父母、带小孩、穷游、一天打卡尽量多等）。
- 同一个需求分别跑**新流程**（Agent）和**旧流程**。旧流程在 `eval/legacy_flow.py` 里**逐行复刻**前端：同一提示词、同样的笔记检索、同一套解析正则、同样的候选名生成与 POI 打分规则。
- “超长路段”两边用**同一口径**：相邻两站公交/地铁时长（无方案时步行）> 60 分钟。

| 指标 | 旧流程 | Agent |
|---|---|---|
| 成功产出行程 | 20/20 | 20/20 |
| 地点匹配到坐标 / 位于目的地 | 100% / 100% | 100% / 100% |
| **超过 60 分钟的路段** | **22.3%（33/148）** | **0%（0/157）** |
| 端到端 P50 / P95 | 27s / 32s | 31s / 40s |

| Agent 指标 | 数值 |
|---|---|
| 工具调用成功率 | 100%（462/462，含客户端重试；原始 QPS 超限 4 次） |
| 首次提交通过 → 自纠后通过 | 80%（16/20）→ 100%（20/20） |
| 平均修正次数 / LLM 轮数 | 0.20 / 6.8 |
| 平均 token / 次 | 56,861（输入约 5.4 万、输出约 0.3 万） |

**要主动讲清楚的两点（诚实的边界）：**
1. **地理匹配率没有提升**——旧流程在这批用例上已经是 100%，因为提示词要求写 `[城市]`，三级匹配 185 个地点里 184 个走的是“同城 POI”。所以简历不写“地理匹配率提升”。
2. **0% 超长路段是校验规则保证的**，不是模型自己变聪明了；能讲的是“旧流程有 22.3% 的路段不可执行，加入校验 + 自纠后全部满足约束，且只用了平均 0.2 次修正”。

### 3.6 遇到的问题

1. **高德 QPS 限流（10021）**：模型同一轮并行发 7~8 个 `poi_search`，个人 Key 每秒配额不够，一半请求失败，模型被迫在后几轮反复重搜同一批地点。最初还把 10021 当成不可重试的业务错误。修复：客户端固定间隔限速（3 QPS）+ 把 10019/10020/10021 归为可重试；10 个并发搜索全部成功。**教训：工具并发要和下游配额匹配；错误分类要区分“稍后会好”和“永远不会好”。**
2. **步数预算耗尽（v1 长沙用例失败）**：复现发现模型要花约 8 轮收集信息（笔记 2 轮、POI 3 轮、路线 3 轮）才第一次提交，12 轮预算里一旦需要修正或多搜一轮就会超限。修复：剩余轮数只够“提交 + 修正”时用 `tool_choice` 强制提交；提示词说明服务端会算所有路段、`route_plan` 最多 4 次。效果（v1 → v2）：成功 19/20 → 20/20，route_plan 284 → 93 次（-67%），token -21%，P95 56s → 40s。
3. **前端调用顺序 bug**：第一版把 Agent 调用插在“风格识别”之前，Agent 拿不到风格提示；在浏览器里发现“偏好识别”消息缺失后定位并调整。
4. **评测公平性**：旧流程不能随手写个简化版来对比，那样会“打稻草人”；所以逐行移植前端逻辑，连 `dedupeList` 会丢掉空字符串这种细节都保持一致。

### 3.7 可能被问到的问题

- **Q：工具调用成功率 100% 是不是太理想？** A：口径是“工具最终返回给模型的结果没有报错”，包含客户端重试；运行中高德原始返回了 4 次 QPS 超限，都被重试恢复。如果按“首次请求成功率”算会低一点，报告里写明了。
- **Q：模型不调用工具、直接输出文字怎么办？** A：提醒它调用 `submit_itinerary`，最多提醒 2 次；预算快用完时用 `tool_choice` 强制调用。
- **Q：一轮里模型同时提交了多次行程？** A：只校验最后一次，其余返回“已忽略”，保证每个 tool_call 都有对应的 tool 消息（否则下一轮 API 会报错）。
- **Q：修正 2 次还不通过怎么办？** A：返回行程并把剩余问题写进 `warnings`，前端提示“部分问题未能自动修正”，不让用户什么都拿不到。
- **Q：为什么延迟比旧流程高？** A：多了工具调用与校验（P50 +4s）；换来的是坐标可信与路线可执行。用 SSE 实时展示进度，用户感知的是“在干活”而不是卡住。
- **Q：怎么判断地点在不在目的地？** A：比较 adcode 前缀：普通城市取前 4 位；直辖市（11/12/31/50 开头）和省级目的地取前 2 位，因为北京城区 adcode 是 1101xx，而北京市本身是 110000。
- **Q：多轮修改怎么保证不推翻原行程？** A：把上一版结构化行程放进提示词并要求“未提到的部分尽量保留”；上一版的地点预先登记，模型可直接沿用 `poi_id`，不必重新搜索。实测“去掉大雁塔换喝茶的地方”只换了一个点，15 秒完成。

## 4. P4 意图分类微调

### 4.1 做之前的状态

- 旧模型：PaddleNLP 上微调 ERNIE 做 8 分类，训练数据是 217 篇小红书游记长文（平均 411 字），推理时的输入却是“出发地：…；目的地：…；偏好：…”这种表单短串——**训练和推理分布完全不同**，效果差是必然的。
- 每类只有 19~45 条，标签也有 15% 前后不一致，拍照和 Vlog 难以区分，“智能综合”是个兜底类。

### 4.2 做了什么

| 环节 | 做法 | 代码 |
|---|---|---|
| 标签重设计 | 风格改为 6 类**多标签**（food / nature / culture / citywalk / photo / rush），拍照与 Vlog 合并，“综合” = 全部不命中；新增 5 类**路由**（plan / notes_qa / graph_qa / realtime / chitchat），供 P5 动态路由 | `classifier/labels.py` |
| 统一输入格式 | `format_input(目的地, 偏好, 原话)` 一个函数，训练数据生成、线上推理、评测都走它，从代码上杜绝分布错配 | `classifier/labels.py` |
| 数据构造 | DeepSeek 按指定意图生成：风格 160 批（标签组合随机：1 个 50%、2 个 35%、3 个 5%、无 10%）、路由每类 20 批（含易混边界）；输入形态混合（只有原话 / 偏好 + 原话 / 只有偏好） | `classifier/train/gen_data.py` |
| 防泄漏 | 测试集**分开生成**：不同提示词（口语、错别字、否定）、15 个训练集没出现过的城市；bge 余弦 ≥0.92 的近重复去掉，测试样本与任何训练样本 ≥0.90 的剔除 | 同上 |
| 训练 | 纯 PyTorch 循环：编码器 CLS + 线性头；多标签 BCE + pos_weight（正样本少的标签加权）；分类头学习率 ×30；warmup 10% + 线性衰减；梯度裁剪；按验证集选最优 epoch；多标签阈值在验证集上逐标签调 | `classifier/train/train.py` |
| 对照 | 句向量 + 逻辑回归、bge-small 微调（5 / 10 轮）、chinese-roberta-wwm-ext 微调、DeepSeek 零样本，同一测试集同一指标 | `train.py`、`eval_llm.py` |
| 级联分析 | 本地模型置信就用本地，否则交给 LLM；阈值在验证集上选 | `classifier/train/report.py` |
| 上线 | `/classify`：本地模型优先、缺失时退回 LLM；返回兼容前端旧的 8 类风格提示词；路由只对聊天原话做 | `classifier/service.py` |

数据规模：风格训练 1367（含 10% 验证）、测试 250；路由训练 1047、测试 220。

### 4.3 关键设计决策

1. **为什么用 LLM 造数据？** 没有真实用户请求日志；人工写上千条不现实。用 LLM 按“指定意图”生成，再用分开生成的测试集 + 人工盲审控制质量。上线后应该用真实请求替换。
2. **为什么要多标签？** “带爸妈去吃本地小吃顺便拍照”同时是 food + photo；单标签会逼模型二选一。
3. **为什么不用 HF Trainer？** 依赖少（不用 accelerate），每一步（加权 loss、分层学习率、按验证集保存）都能讲清楚。
4. **为什么部署 RoBERTa 而不是更快的 bge-small？** 验证集上 RoBERTa 两个任务都最好；43ms / 23ms 对接口来说完全够用。bge-small 只要 8ms、96MB，是资源受限时的备选。
5. **为什么级联最后选了“全部本地”？** 阈值只能在验证集上选；验证集上本地模型已经足够好，加 LLM 没有收益。测试集上某些阈值看起来更好（路由 0.972），但那是看着测试集挑的，不能用。

### 4.4 怎么验证的

- 同一测试集、同一指标对比 5 种方法；模型、epoch、阈值、级联阈值全部只在验证集上决定。
- 上线前用 7 条典型输入通过网关实测（见 4.6 第 4、5 条发现的问题）。
- 单元测试覆盖输入格式、多标签指标与“综合”类、阈值搜索、模型缺失时退回 LLM、多标签映射到前端旧标签、路由只用于聊天消息。

### 4.5 结果（`eval/classifier_report.md`，测试标签待人工盲审）

**风格（多标签，测试 250 条，含 28 条“综合”）**

| 方法 | micro-F1 | 整行全对 | “综合”F1 | 单条延迟 |
|---|---|---|---|---|
| 句向量 + 逻辑回归 | 0.727 | 45.2% | 0.678 | 10ms |
| bge-small 微调 | 0.770 | 55.2% | 0.667 | 8ms |
| **RoBERTa 微调** | **0.805** | **60.4%** | **0.828** | 43ms |
| DeepSeek 零样本 | 0.797 | 55.6% | 0.745 | ~1s |

**路由（单标签，测试 220 条）**

| 方法 | macro-F1 | 单条延迟 |
|---|---|---|
| 句向量 + 逻辑回归 | 0.941 | 11ms |
| bge-small 微调 | 0.940 | 5ms |
| RoBERTa 微调 | 0.954 | 23ms |
| **DeepSeek 零样本** | **0.967** | ~0.8s |

**一句话版本：** 风格多标签上微调 RoBERTa 略超 DeepSeek 零样本（micro-F1 0.805 vs 0.797，整行全对 60.4% vs 55.6%），延迟从约 1 秒降到 43 毫秒；路由上比 LLM 低 1.3 个点，换来 35 倍速度和零调用成本。

**要主动讲的边界：** 测试标签是生成意图，且由同一个 LLM 生成——这对 LLM 零样本是“主场优势”，对比可能偏向 LLM；人工盲审会给出标签噪声水平。

### 4.6 遇到的问题（讲故事用）

1. **测试集里没有“综合”样本**：所有方法的“综合”F1 都是 0，包括 LLM——这不正常。排查发现测试集 222 条里“综合”样本为 0（训练集有 154 条）——测试集只有 24 批、按 10% 概率随机抽“无标签”批次，最终没有产出任何“综合”样本。补生成 28 条（同样的测试集流程、同样去重）后，“综合”F1 才有意义，而且暴露了 LLM 恰恰在这一类上最弱（0.745）。**教训：指标全是 0 或全是 1 时先查数据，不要先怀疑模型。**
2. **LLM 延迟测量失真**：第一次测出 12.5 秒，因为 220 个请求同时发出、在并发闸门（8）里排队。改为顺序调用 20 条测单次延迟：约 0.8~1 秒。
3. **用测试集选模型的泄漏**：第一版报告按测试集分数挑“最佳模型”做级联分析——改为按验证集。级联阈值也改为在验证集上选，结果是“全部本地”，于是不宣称级联收益。
4. **路由模型在分布外输入上“自信地错”**：上线抽查发现表单拼接输入被判成 chitchat，置信度 0.99。路由模型只见过单句消息。处理：路由只用于聊天原话。**教训：高置信度不等于正确，分布外输入要在调用侧拦住。**
5. **“综合”仍有个例漏判**：“经典景点都去看看就行”被判成 nature + culture + rush。整体 F1 不错不代表典型样本没问题；后续可以加“综合”样本或“命中 3 个及以上降级为综合”的规则。
6. **一次延迟异常**：RoBERTa 风格模型训练完立即测得 517ms，复测 43ms（训练刚结束时内存与 CPU 状态影响）；最终报告用复测值，评测脚本加了预热。

### 4.7 可能被问到的问题

- **Q：为什么本地模型能超过 LLM？** A：只在风格任务上略超，主要赢在“综合”类（0.828 vs 0.745）——LLM 对“综合”的召回只有 0.68（28 条里有 9 条硬找出了风格），平均每条预测 1.52 个标签而真实是 1.43；微调模型从训练数据里学到了“无明显风格”的分布。路由任务上 LLM 仍更好。
- **Q：多标签阈值怎么定？** A：每个标签在验证集上从 0.2~0.8 网格搜索使 F1 最大的阈值，而不是统一用 0.5；正样本少的标签阈值通常更低。
- **Q：怎么保证测试集不泄漏？** A：分开生成（不同提示词）、只用训练集未出现的城市、与训练样本 bge 相似度 ≥0.90 的剔除；模型选择只看验证集。
- **Q：数据是 LLM 生成的，模型学的是不是 LLM 的口吻？** A：有这个风险，所以测试集刻意改成更口语、带错别字和否定的写法；真正的解决办法是上线后收集真实请求做抽样标注，这在报告里写为后续工作。
- **Q：CPU 上训练要多久？** A：bge-small 风格 5 轮约 3 分钟；RoBERTa 风格约 43 分钟、路由约 9 分钟（12 线程 CPU，没有 GPU）。
