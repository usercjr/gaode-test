### 修复记录：熔断打开后仍然很慢

第一次压测（`eval/load_test_v1.md`）中，熔断已经打开、上游调用次数为 0 的请求仍然要 **1.0~1.8 秒**才返回。
原因：熔断器拒绝时抛出的错误码是“暂时不可用（可重试）”，重试逻辑对它做了两次指数退避（0.5s + 1s）。
修复：熔断拒绝改为单独的 `CircuitOpenError`，重试逻辑遇到它立即放弃（对用户的提示语和错误码不变）。

| 熔断打开后的请求 | 修复前 | 修复后 |
|---|---|---|
| 耗时 | 993~1793 ms | 33~75 ms |
| 打到上游的次数 | 0 | 0 |

## 说明

- 吞吐和延迟受本机 CPU 影响，换机器数值会变；这里关注的是**随并发变化的趋势**和**保护机制是否按设计生效**。
- 聊天吞吐的上限由 LLM 并发闸门决定（约 并发上限 ÷ 单次 LLM 耗时），真实环境下还受 DeepSeek 自身限流影响。
- 检索是 CPU 密集计算，在线程池中执行；单进程下并发提高后吞吐有限，扩容需要多进程 / 多实例。
